## Language and Governance Policy
**Language setting:** `English / 英文`
Language rules are an absolute hard-execution requirement: unless the current request explicitly asks for another language, translation, bilingual output, or preserved source text, all newly generated natural-language content intended for the user must be in English.
Scope covers responses, status updates, clarification questions, summaries, reviews, generated documents, requirements, plans, tasks, change notes, commit messages, and PR text.
Code identifiers, commands, paths, config keys, environment variables, API names, protocol names, logs, tool output, and quoted material may remain in their original language; any new explanation, conclusion, or surrounding guidance must follow this language setting.
The source language of skills, agents, templates, historical context, or examples must not override this setting; new code comments also follow this setting and explain only non-obvious intent.
### External Output Privacy and Attribution
Never automatically add workflow, tool, skill, agent, model, vendor, or generation-method names, attribution, links, footers, badges, or promotional text to newly generated user-facing or external artifacts, including pull requests, issues, commits, release notes, changelogs, reports, plans, specifications, and business documents.
Never automatically add `Built with`, `Generated by`, `Powered by`, AI authorship, or co-author trailers. Add a specific attribution only when the user explicitly requests that exact attribution in the current turn.
### Workflow Entry Governance

## Execution Rules for Agents

These rules apply to every agent working in this repository. They override a workflow skill's
defaults and any suite instruction inside a plan or a product document. Reusable standards are in
[`docs/development.md`](docs/development.md) section 5; architecture is in
[`docs/architecture.md`](docs/architecture.md); operational detail is in
[`docs/operations.md`](docs/operations.md).

### The product
- **Loom** is a Windows-first Electron desktop app hosting the engine daemon. The packages are
  `engine/packages/{daemon,cli,ui,i18n}`, plus `desktop/` and the optional `companions/loom/`.
- Agents run as direct child processes. There is no terminal multiplexer, no shell session and no
  host provisioning; the browser UI is an optional viewer next to the desktop.
- The shipped target is native Windows 10/11 x64 with Node 22 or 24 and Git for Windows. The
  engine also stays portable to Linux, and CI runs both (`smoke.yml`, `tests.yml`).
- Code, scripts and CI contain no user- or machine-specific paths, hosts, proxies or credentials.
  Use the per-user config and state directories.

### Working
- Each unit works in its own worktree, created from current `origin/main`, and never in another
  unit's checkout. Scratch files and logs go under one folder per unit and are removed when the
  unit lands.
- Keep it simple. Load the `karpathy-guidelines` skill when writing, reviewing or refactoring code.
  Build the simplest form that works; add no guard, fallback, option or layer for a case that no
  caller needs. Validate at real boundaries only: worker-written data, external processes, the
  network, files from outside the repository, owner input. Trust typed internal callers. Prefer
  existing code over hand-written replacements, and remove what your change made unused.
- UI copy follows [`docs/development.md`](docs/development.md) section 5 standard 9: no redundant
  labels, captions or helper text; hierarchy, spacing and a clear primary action explain the
  screen. Keep form labels, accessible names and the consequence statement on dangerous actions.
- Remove what your change makes unused: imports, exports, types, i18n keys (with their
  `MESSAGE_PARAMETERS` entries), CSS, docs that describe the deleted code, and tests.
- Comments explain non-obvious intent only. Don't add task, decision or phase IDs to new comments.

### Verification
- Every change runs the focused tests for the code it touched and the touched package's
  typecheck (`npm run lint` in `engine/` covers all four packages). Run `npm run smoke` in
  `engine/` before you finish.
- Run one Vitest process at a time with stdin detached and `--maxWorkers=2`. Leave no Vitest
  process, daemon fixture or engine child running when you finish.
- The full daemon suite is the orchestrator's job, not a unit's. A deletion unit must leave no
  dangling import, so the typecheck and `npm run test:repo` are its gate.
- When you delete a test along with dead code, say so in the pull request. Never weaken a test of
  live code to make it pass; if a live test fails, find the cause.
- Before a pull request claims a line is the cause of a failure, revert that line and run the test.

### Fixing
- Fix a failure with a verified cause directly. A cause is verified when the failure was
  reproduced, or when a failing test or a direct trace points to the responsible line. Keep a test
  that fails for that cause and record the cause in the pull request. The full `spec-debug`
  workflow is only for a failure whose cause is unknown; in this repository this overrides the
  `spec-debug` entry rule in the managed block above.

### Stop rules
Stop and report instead of looping when:
- a slice grows past twice its scope;
- the same fix fails twice;
- an investigation runs 30 minutes without a measured lead;
- the change needs a new public contract or architecture;
- a required tool or credential is missing;
- a deletion turns out to cut live behavior — a UI, CLI or desktop caller, or a background loop the
  packaged desktop actually starts.

### Decide, don't ask
- Decide a question yourself when these rules, the unit's purpose or the launch brief settle it.
  Record the reason in the pull request and continue.
- Ask the owner only about scope beyond the unit, a change to a public contract or architecture, a
  grant these rules don't give, or one of the stops above. Batch the questions.

### Review and delivery
- The orchestrating session reviews every pull request: it reads the diff, runs the unit's demo and
  checks CI. Implementers do not dispatch their own reviewers.
- A change to credential handling or `engine/packages/daemon/src/domain/team-workspace.ts` (the
  reader of worker-written files) also gets one independent, report-only reviewer. It runs one
  round, plus one confirmation of any P0/P1 fix. Give it `engine/config/team/roles/reviewer.md` and
  `engine/config/team/core.md`; [`docs/operations.md`](docs/operations.md) section 10 says how to
  call one.
- A finding that only asks for more hardening, with no reachable scenario in current code, is
  recorded as a residual and not implemented.
- **Standing delivery grant.** Commit the scoped files, push the unit's branch, and open or update
  the pull request without asking. Once the review is done and CI is green, land it with a rebase
  merge.
- A release, a deployment or a version bump needs its own authorization.
- Commits and pull requests carry no tool or AI attribution, no `Co-Authored-By` trailer and no
  "Generated with" line. Don't stash, reset, revert or force-push unless the owner asks; never push
  to the default branch.
- Write no separate report files: the pull request description is the report. Record a decision
  worth keeping in the pull request or in the commit message — never in a plan or a task file.

### On the owner's machine
Everything here is a fact about this one machine and belongs nowhere in the repository.
- Worktrees live under `D:\Loom\work\<unit>`, on their own branch from `origin/main`. Scratch and
  logs go in `D:\Loom\work\<unit>-scratch`.
- Caches live under `D:\Loom\cache\{tmp,npm,electron}`. Put `TEMP`, `TMP` and `npm_config_cache`
  there in every Windows command that installs, builds or tests.
- The C: drive is nearly full: create nothing on it.
- Network access needs the local proxy described in the owner's global instructions; set it for
  that command only. Never write the proxy address into the repository.
- Run every process hidden: use the PowerShell tool directly, and never spawn a visible console
  (`cmd /c start`, or `Start-Process` without `-WindowStyle Hidden`).
